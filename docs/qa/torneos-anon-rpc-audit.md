# Auditoría de nueve RPCs SECURITY DEFINER ejecutables por anon

Fuente: catálogo y `pg_get_functiondef` de Supabase local efímero sobre el esquema canónico. Las nueve funciones tienen `SECURITY DEFINER`, `SET search_path = ''` y privilegio `EXECUTE` para `anon`, pero las nueve rechazan `auth.uid() is null` directa o indirectamente. Por lo tanto, el rol `anon` puede invocarlas, pero una sesión realmente anónima no obtiene datos.

No se modificaron grants ni funciones.

## Conclusión

El riesgo inmediato de acceso anónimo efectivo es bajo porque todas las funciones requieren identidad. El grant a `anon` es innecesario y aumenta superficie/confusión operativa; la recomendación general es revocarlo en una etapa de permisos específicamente autorizada, después de confirmar que los clientes autenticados conservan `EXECUTE`. El riesgo principal a vigilar es regresión cross-tenant dentro de helpers SECURITY DEFINER y exposición de roster/sanciones a usuarios autenticados con acceso al hub.
