# R4.2 — Blocker 1: diagnóstico targeted y fix

Alcance: exclusivamente este worktree. Sin matriz completa, certify, Production, R5,
frontend, B04, commit, push ni PR. La certificación R4.2 sigue pendiente.

## Causa demostrada

`runOutageHarness()` invocaba Docker mediante `spawnSync()` en el mismo hilo que
Node/Undici. Durante ese bloqueo el proxy de ingreso cerraba normalmente las conexiones
HTTP inactivas (`keepAliveTimeout=5000`, `keepAliveTimeoutBuffer=1000`). El event loop del
cliente no podía procesar el EOF ni sus temporizadores. Al volver del harness, el pool podía
elegir un socket que aún consideraba abierto, aunque el proxy ya lo había cerrado.
El primer POST `/torneos-gateway/exchange` escribía en ese socket y terminaba en
`TypeError: fetch failed`, causa `SocketError / UND_ERR_SOCKET / other side closed`.

No es un fallo del contrato, Core unavailable ni gateway 503: no hubo respuesta HTTP.
El proxy y gateway permanecieron vivos. El cierre fue de una conexión por inactividad,
no una caída del proceso. No se inyectó ningún fallo Auth/contract ni se cambió una ruta.

La causa se reprodujo con el gateway real. Los controles adicionales prueban que **no
requiere el contenido del harness offline**: basta bloquear el hilo principal durante
8 segundos con sockets precalentados. Una espera asíncrona equivalente funciona.
[Node documenta que spawnSync bloquea el event loop](https://nodejs.org/api/child_process.html#synchronous-process-creation).

  sus logs sí registran las solicitudes de health antes/después y los exchanges de control.
  No llegó al handler de ingreso del proxy, por lo que no fue reenviada al gateway.

`20260920T170732Z` no tenía este trazado; no se inventa evidencia retrospectiva sobre
si su request llegó al gateway. Su secuencia y error coinciden con el mecanismo reproducido.

## Reproducción mínima y validación posterior

Entrypoint dedicado, incapaz de seleccionar la matriz o certify:

```sh
node backend/torneos/phase3b/r42/run-transport.mjs diagnosis
node backend/torneos/phase3b/r42/run-transport.mjs postfix
```

Ejecutar desde este worktree. Usa el PAT existente del Keychain y los mecanismos de
custodia existentes, exclusivamente en memoria. Cada ejecución crea un usuario QA staging,
hace startup/smoke, llama health/exchange y elimina QA, sesiones e identidades al terminar.
No crea fixtures. No altera TTL, sesiones, D1, allowlist ni cache.

`diagnosis` compara A/B/C/D y una repetición B. La versión final precalienta dos sockets
antes de cada caso para controlar la disponibilidad del pool. `postfix` compara:

| Caso | Operación entre health y exchange | Resultado |
|---|---|---|
| A | Ninguna; ocho exchanges normales | 8/8 HTTP 200 |
| E ×3 | Proceso síncrono inactivo 8 s; ningún harness | 3/3 UND_ERR_SOCKET |
| F | Espera asíncrona 8 s; dispatcher original | HTTP 200 |
| G ×2 | Harness real en worker; dispatcher original | 2/2 HTTP 200; 29/29 offline cada vez |

Cada exchange se intenta una vez. Los health posteriores son sondas separadas y
explícitas, en conexión independiente; no reintentan el exchange fallido.
El observador usa diagnostics_channel y eventos de socket, más listeners metadata-only
en el proxy temporal. No registra cuerpos, headers de autorización ni secretos. El inspector
sólo escucha en loopback del container y desaparece con su cleanup; no hay puerto publicado.

## Fix mínimo

- `outage.mjs`: agrega `runOutageHarnessAsync()`; ejecuta el harness existente en un worker.
- `outage-worker.mjs`: recibe únicamente el label público del run y devuelve el resultado.
- `matrix.mjs`: cambia la llamada a `await runOutageHarnessAsync({label: run})`.

La implementación offline original, su bundle, sus 29 casos y límites de ejecución se
conservan. El worker deja al hilo principal procesar los cierres y temporizadores del pool
antes de emitir la primera solicitud posterior. No se agregaron retries, delays de recuperación,
reemplazo de dispatcher en la matriz ni cambios al gateway/proxy.

Este fix cubre la pausa síncrona demostrada; no certifica otros bloques de R4.2 ni excluye
que otras pausas síncronas largas requieran diagnóstico si aparecen en otro escenario.

## Integridad del diagnóstico

El intento `20260920T214408Z` es **inválido como control de transporte original**:
mi primer cierre del inspector usó una importación dinámica no admitida y terminó el proxy
con `ERR_VM_DYNAMIC_IMPORT_CALLBACK_MISSING`. Se interrumpió el harness restante,
se ejecutó cleanup, se verificaron QA/sesiones y R2, y se corrigió el observador.
Sus artefactos se conservaron y no se usan para concluir la causa original.

En `20260920T214654Z`, `ip -j` no estaba soportado por la imagen auxiliar: el campo
`gatewayRoutesAndTCP` contiene TCP, no rutas. No se presenta como prueba de rutas estables.
La captura fue corregida a `ip -f inet route`, exige `unreachable default`, y se verifica
antes/después y en cada fallo E de la validación posterior.

La primera validación posterior `20260920T220907Z` obtuvo 200 en los dos exchanges
posteriores al worker, pero su revisión encontró además dos `UND_ERR_SOCKET` en sondas
warm **anteriores** al worker. Las capturas Docker síncronas agrupadas del propio observador
también bloqueaban el event loop. Ese PASS tenía alcance insuficiente: no comprobaba todas
las sondas warm. Se conservaron sus artefactos, se hicieron asíncronas todas las capturas,
y se agregó la condición explícita de **cero fallos inesperados** a productor y verificador.
La validación final referenciada abajo reemplaza esa evidencia para declarar el resultado targeted.

Los primeros summaries tienen el nombre heredado `R4_MINIMAL_*`: describen la recolección
que ejecutaron, no certificación. La versión final usa `R42_TRANSPORT_PASS/FAIL`.
El verificador independiente comprueba el cierre previo, contadores de bytes, una tentativa,
ausencia/presencia en el proxy, procesos, rutas, health y cleanup.
