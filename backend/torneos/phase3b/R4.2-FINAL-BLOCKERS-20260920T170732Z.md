## 1. Blocker 1: hallazgo final y límites

El error observado ahora nace en **Node/Undici del host**, en `guardedFetch()` (`r42/lib.mjs`):
`TypeError: fetch failed`, causa `UND_ERR_SOCKET` / `SocketError`, sin respuesta HTTP.
La URL es **/torneos-gateway/exchange**, no el RPC de outage. La secuencia es
`check live → tok(owner) → exchange(owner) → gw(/exchange) → guardedFetch → fetch`.
Ocurre **antes de entrar a withCoreFault('contract')**, inmediatamente después del harness offline
síncrono. Por lo tanto, en este run la inyección contractual aún no se había aplicado.
No hay evidencia para afirmar que el gateway recibió esa solicitud o produjo una respuesta;
lo demostrado es que el fetch del host no obtuvo ninguna respuesta HTTP.

La reutilización de una conexión keep-alive cerrada durante el bloqueo síncrono del harness
es una hipótesis compatible con la secuencia, **no una causa exacta demostrada**. No se aplicó
un fix para esa hipótesis ni se ejecutó otro experimento después del STOP.
El blocker 1 permanece abierto. No corresponde atribuir este error a la conversión upstream→503
del gateway ni declarar que fue corregido.

En el run histórico 20260920T165201Z, sólo se guardó `fetch failed`: no quedaron URL ni errno.
No se puede determinar retrospectivamente si falló el refresh previo o el RPC durante la inyección.
**Corrección de la interpretación preliminar:** la topología de rutas defectuosa está demostrada,
pero no prueba por sí sola la causa de ese fetch histórico. El diagnóstico preliminar
`r42-final-blockers-diagnosis-20260920T170732Z.json` se conserva intacto; este informe delimita su conclusión
con la evidencia posterior.

Sí se demostró un defecto independiente del harness: al eliminar la ruta /32 al proxy de Core,
también se elimina la ruta de retorno gateway→proxy de ingreso. El control sintético reprodujo
`200 → 503 UNAVAILABLE sin no-store → 200`, con `ip route get` devolviendo `Host is unreachable`.
El servidor sintético recibió una solicitud durante el corte; esto confirma que no debe confundirse
«sin respuesta HTTP en el host» con «el handler no se ejecutó».

El fix aplicado para esa topología separa Auth y contrato mediante resets por ruta HTTP en el
proxy propio del run, sin modificar rutas de ingreso. Además corrige la aserción contractual
anterior (`503 access denied`) a `503 CORE_UNAVAILABLE`. La caída Auth y recuperación inmediata
pasaron live. La caída contractual nueva quedó sin ejecutar por el fallo previo en exchange.

## 2. Blocker 2: causa y fix

Las tres respuestas históricas sin header fueron las del outage Auth: `/health`, `/exchange` y
`/torneos/rest/v1/rpc/get_my_tournament_memberships`. El RPC tenía cuerpo literal `UNAVAILABLE`;
es la respuesta propia del **proxy de ingreso**, cuyo manejador de error emitía `writeHead(503)`
sin Cache-Control. No era el JSON del gateway. La reproducción aislada confirma ese mecanismo.

El gateway ya establece NO_STORE tanto en `json()` como en su passthrough REST. Sus fuentes no
cambiaron respecto del sello aceptado anterior. El fix mínimo establece `Cache-Control: no-store`
al entrar al proxy de ingreso y lo fuerza también al copiar headers del upstream. Cubre errores
propios y respuestas reenviadas. No se agregó cache ni se cambió el contrato de sesiones o TTL.

En el run abortado, **178 respuestas / 0 violaciones**. No se declara PASS de la matriz no_cache,
porque no se alcanzó ese bloque ni todas las clases live.
