### 1.1 Duración medida del routeHelper síncrono (el par `ip route del` + `routes()`)

- Caso B: 121 + 149 = **270 ms**; B-repeat: 353 + 212 = **565 ms**; B-loaded (justo después del harness offline y del
  fault de contrato, secuencia idéntica a la matriz): **265 / 268 ms**. `ip route replace`: 128–151 ms.
- Muestreo aparte (12 pares contra un namespace descartable): min 279 / mediana 299 / max 313 ms.
- La sesión anterior midió el mismo par en **2.7–3.0 s** («en reposo»). La latencia de `docker run --rm` en esta máquina
  varía ≥10× entre momentos; hoy no se pudo provocar un momento lento.

### 1.2 Keep-alive observado (dos lados)

- Proxy de ingreso (`http.Server` de Node): evento `server` → `keepAliveTimeout 5000`, **`keepAliveTimeoutBuffer 1000`**,
  header `Keep-Alive: timeout=5`. **El socket se cierra realmente a 6.0 s de idle**: `timeout`+`close` de 61022 a los
  6.008 s de su última respuesta (`234910Z`: 61470 a 6.002 s).
- Cliente (Node v25.2.1, undici 7.16.0): con el loop libre undici destruye el socket idle a **~3.0 s** (hint 5 s − umbral
  2 s; IDLE: `client:socket:close@3001ms`, B-warm 55142 cerrado a 3.27 s). Un loop libre nunca deja que un socket
  del pool llegue a los 6 s del proxy.
- Alternancia de sockets (confirmada puerto a puerto en los 5 runs): con `pipelining:1` undici difiere el `resume` del
  socket recién usado con `setImmediate`; la request siguiente, si se despacha sin vuelta del loop (microtasks +
  `spawnSync`), toma **el otro socket del pool**, cuyo idle empezó en su respuesta anterior (δ), no en la última.
  En la secuencia de la matriz el socket elegido es el del `503 CORE_UNAVAILABLE` del check anterior: δ ≈ 1.0–1.6 s.

### 1.3 Dónde muere el socket (B-padded, `r42-route-transport-20260920T235245Z.json`)

Secuencia idéntica a la matriz: `pre-health` (61030) → `pre-rpc-corefault` 503 CORE_UNAVAILABLE (**61022**, 0.382 s) →
`ctl` sync 48 ms → `routes()` sync 125 ms → `pre-recovery` 200 (61030, 1.140 s) → `ip route del` sync 119 ms →
`routes()` sync 160 ms → bloqueo sync hasta 6.305 s de idle de 61022 → dispatch.

- Proxy: `timeout` + `close` de 61022 a **6.390 s** (bw=1342, br=3832, `hadError=false`); **no existe evento `request`
  para `B-padded-rpc`**: la request no llegó al handler del proxy ni al gateway.
- Cliente: `undici:client:sendHeaders` sobre lp 63913 (bw=3832, br=1342 = espejo exacto de 61022 a través del NAT de
  Docker), `readyState open`, `destroyed=false`; escribe 1192 bytes (bw 3832→5024); en el mismo milisegundo procesa el
  FIN pendiente → `client:socket:end` → `SocketError: other side closed` → `undici:request:error UND_ERR_SOCKET`.
  `fetch failed` a los **129 ms** del dispatch. Un solo intento (`oneAttemptEach=true`).
- En el momento del error: gateway `7f0917551c5b` y proxy `f600622372dd` `running`, `RestartCount 0`, mismo `StartedAt`
  antes/después, sin OOM. Rutas durante el fault = REST /32 ausente; restauradas e idénticas al baseline después.
- Recovery (primer RPC posterior, sobre el otro socket): **200**. Health después: 200.
- Loop: 3 ticks en 5.5 s, gap máximo 5549 ms (bloqueado). C-padded (mismos comandos, mismo tiempo total, loop libre):
  235 ticks, gap máximo 53 ms → 503 `access denied` + `no-store`, tabla 503 + `no-store`, recovery 200.

### 1.4 Causa demostrada

`UND_ERR_SOCKET` = despacho sobre un socket del pool que el proxy ya cerró por idle (6.0 s) **mientras el event loop
estaba bloqueado**, de modo que ni el cierre propio de undici (3 s) ni el FIN pudieron procesarse antes de escribir.
Condición: bloqueo sincrónico continuo ≥ 6.0 s − δ entre la última respuesta y el dispatch (con δ ≈ 1.0–1.6 s: ≥ 4.4–5 s;
con Docker lento también en el preámbulo, δ crece hasta ~3 s y bastan ≥ 3 s). La única fuente sincrónica en ese
tramo de la matriz eran los dos `spawnSync docker run` de `withRouteRemoved`.

Queda **excluido** el cierre en vuelo: 5/5 RPC con la ruta removida estuvieron 5.6–6.3 s en vuelo (el gateway espera
su `AbortSignal.timeout(5000)` porque la conexión pooled a REST no falla con ENETUNREACH, sólo deja de transmitir)
sobre sockets con hasta 7.2 s desde su respuesta anterior, y todos obtuvieron 503: el proxy resetea su timer al recibir
la request.

**Lo que NO se demostró:** que el par real haya tardado ≥ 4.4 s en el run `230313Z`. Hoy tardó 0.27–0.57 s; la sesión
anterior lo midió en 2.7–3.0 s; el log del run (`block` 23:07:11 → `FAIL` 23:07:17, con el `replace` sync incluido)
acota el bloqueo a 3.6–6.85 s. Es la única secuencia compatible con la evidencia; la latencia de Docker en ese
instante es inferida, no reproducida.

## 2. Fix mínimo (aplicado, SIN COMMIT)

`finally` de rollback, mismo número de requests HTTP, sin retries, sin dispatcher ni `Connection: close`.

- [r42/route-fault.mjs](r42/route-fault.mjs) (nuevo): `routeHelperArgs`, `normalizeHostRoute`, `routeFault({run, gateway,
  routes, exec})` → `{routeHelper, routes, withRouteRemoved}`; `exec` = `d` (histórico) o `dAsync` (default).
  Test offline: argumentos byte-idénticos al helper inline histórico; del → routes → fn → replace en `finally` aun si
  `fn` lanza; el loop sigue vivo con `exec` async.
- [r42/lib.mjs](r42/lib.mjs): `callAsync`/`dAsync` con el contrato de `call()` (env, timeout, SIGKILL, `COMMAND_FAILED`);
  `causeMessage` en `HTTP_TRANSPORT_FAILED`.

  Sin cambios en gateway, proxy, contratos Core, TTL, sesiones, D1, allowlist, network policy ni semántica REST.

## 4. Blocker aparte — el assert del bloque no puede pasar contra el gateway sellado

`matrix.mjs` afirma `rpcBody.error === 'TORNEOS_UNAVAILABLE'`. El gateway sellado (`cc5b1d45…`) devuelve para este RPC
**`503 {"error":"access denied"}`**: `get_my_tournament_memberships` no está en `CONTRACTS`, va por `proxy()` →
`dependencyFetch` falla → `Unavailable` → `index.ts:231`. Evidencia: 9/9 RPC con la ruta removida en esta sesión,
la única vez que el bloque pasó live (`r4-matrix-detail-20260920T165201Z`: `rpcBody {"error":"access denied"}`) y el
informe FINAL-BLOCKERS §2 («el wire error existente sigue siendo `503 access denied`; TORNEOS_UNAVAILABLE es el
escenario, no un código»). `TORNEOS_UNAVAILABLE` sólo existe en `adapter.ts` para los RPC con contrato Core.
**No toqué ese assert**: cambiarlo a `'access denied'` alinea la matriz con el contrato certificado; cambiar el gateway
está fuera de alcance (sello R4.1A). Decisión de Nico antes del próximo full run; con el assert actual el bloque
falla aunque el transporte esté corregido.
